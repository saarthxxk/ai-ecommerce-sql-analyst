# AI E-commerce SQL Analyst

An LLM-powered natural-language data analyst for an e-commerce dataset. Ask a
question in plain English; a LangGraph agent classifies it, reads the live
PostgreSQL schema, writes SQL with an LLM, validates that SQL in Python,
executes it through a read-only database role, analyses the result with
pandas, and returns the SQL, the data, and a concise natural-language answer
through a REST API.

## Project overview

**Problem:** answering a question about an e-commerce store's data normally
means someone who knows SQL sitting down and writing a query. **Solution:**
let the question be asked in English, and have an explicit, inspectable agent
workflow turn it into a safe, correct SQL query against the real schema, then
turn the result back into a sentence — without ever trusting the LLM to
touch the database directly, invent a column, or invent a number.

The project prioritises a working, explainable MVP over feature breadth: one
straightforward LangGraph workflow, one validator, one executor, all backed by
tests that need no API key.

## Dataset

Six CSVs in `ecommerce_dataset/`, loaded as-is (columns were not renamed or
invented — see `app/database/schema.sql` for the exact DDL derived from them).
Row counts below are what actually loaded into PostgreSQL:

| table | rows | primary key | notes |
|---|---|---|---|
| `users` | 10,000 | `user_id` | customer profiles |
| `products` | 2,000 | `product_id` | catalog, price, catalog rating |
| `orders` | 20,000 | `order_id` | order headers |
| `order_items` | 43,525 | `order_item_id` | line items — this is the revenue table |
| `reviews` | 15,000 | `review_id` | 1–5 rating + review text |
| `events` | 80,000 | `event_id` | view / cart / wishlist / purchase log |

Measured data quality (`reports/data_quality.json`, regenerated by
`scripts/load_data.py`): **zero missing values, zero duplicate rows, zero
foreign-key orphans** across every relationship, and `orders.total_amount`
matches `SUM(order_items.item_total)` exactly for all 20,000 orders.

One deliberate deviation from a generic e-commerce schema, discovered by
inspecting the CSVs rather than assumed: **`events` has no `order_id`** and
cannot be joined to `orders`/`order_items`. The browse-to-buy funnel lives
entirely in `events`; monetary revenue lives entirely in `order_items`. See
`docs/database_guide.md` for the full write-up, which the SQL-generation
prompt also carries.

## Database schema

Every table, column, foreign key and index below was derived from the actual
CSVs (see `scripts/data_quality.py` output), not assumed:

```
users (user_id PK)
 ├──< orders (order_id PK, user_id FK)
 │      └──< order_items (order_item_id PK, order_id FK, product_id FK, user_id FK)
 ├──< order_items (user_id FK — denormalised copy of orders.user_id)
 ├──< reviews (review_id PK, order_id FK, product_id FK, user_id FK)
 └──< events (event_id PK, user_id FK, product_id FK)

products (product_id PK)
 ├──< order_items (product_id FK)
 ├──< reviews (product_id FK)
 └──< events (product_id FK)
```

`GET /schema` returns this same information live from PostgreSQL's catalog —
nothing about the schema is hardcoded in the application. Full column-level
detail and business definitions (what "revenue" means, why `events` can't
join to `orders`, etc.) are in `docs/database_guide.md`, and the same
definitions are embedded as `COMMENT ON TABLE/COLUMN` in
`app/database/schema.sql`, which the LLM prompt reads back out.

## Agent workflow

Built with LangGraph as an explicit state machine (`app/agent/graph.py`,
`app/agent/state.py`):

```
START
  │
  ▼
classify_question ──[GENERAL_QUERY]──▶ general_answer ──▶ END
  │
 [DATABASE_QUERY]
  │
  ▼
retrieve_schema ──▶ generate_sql ──▶ validate_sql
                         ▲               │
                         │          [invalid, attempts<2]
                         └───────────────┘
                                    │
                               [valid]
                                    ▼
                              execute_sql
                         ▲               │
                         │          [db error, attempts<2]
                         └───────────────┘
                                    │
                               [rows]
                                    ▼
                            analyze_result ──▶ generate_answer ──▶ END
```

- **classify_question** — is this a question about the store's data, or a
  general/conceptual question ("What is SQL?")? Only the former touches the
  database.
- **retrieve_schema** — reads the live PostgreSQL catalog
  (`app/database/schema_inspector.py`), never a hardcoded schema string.
- **generate_sql** — LangChain + Gemini writes one PostgreSQL `SELECT`
  against that schema, returned as structured JSON
  (`app/services/sql_generator.py`).
- **validate_sql** — Python-only safety gate, independent of the prompt
  (`app/services/sql_validator.py`); see Security below.
- **execute_sql** — runs through a read-only role with a statement timeout
  and a row cap (`app/database/executor.py`).
- If validation or execution fails, the graph loops back to `generate_sql`
  **exactly once** with the error attached, then gives up cleanly — no
  unbounded retry loop.
- **analyze_result** — pandas computes the actual numbers (extremes,
  percentage changes, trend direction) so the LLM never does arithmetic
  (`app/services/result_analyzer.py`).
- **generate_answer** — the LLM turns the question + the computed facts +
  the actual rows into 1–5 sentences, explicitly barred from stating any
  number not present in that material (`app/services/answer_generator.py`).

The agent's only database access is through three bounded LangChain tools
(`app/agent/tools.py`): `get_database_schema()`, `execute_read_only_sql()`
(validator-gated), and `get_table_statistics()`. The model is never handed a
connection.

## Tech stack

| tool | why |
|---|---|
| **FastAPI** | typed request/response models, automatic `/docs`, dependency injection used to swap in test doubles |
| **PostgreSQL** | real relational engine with enforceable role-based read-only access — not just a validator's promise |
| **SQLAlchemy + psycopg3** | connection pooling, per-connection `statement_timeout`, no raw string interpolation of SQL |
| **pandas** | the entire numeric layer (extremes, trends, % change) is computed deterministically here, not by the LLM |
| **sqlglot** | parses LLM-generated SQL into an AST so the validator can reject write operations structurally, not just by keyword-matching |
| **LangChain** | prompt templates, structured output parsing, and a provider-agnostic `BaseChatModel` interface (Gemini/Vertex/OpenAI/fake are interchangeable) |
| **LangGraph** | the agent workflow is an explicit, inspectable state graph with conditional routing and a bounded retry — not a hidden agent loop |
| **Gemini (Google AI Studio)** | default LLM provider; Vertex AI and OpenAI are supported via the same interface |
| **pytest** | 51 tests run with no API key and no live database, using a deterministic offline `FakeChatModel` that is a real `BaseChatModel`, not a mock |

## Setup

### 1. PostgreSQL

Either use an existing local PostgreSQL install, or start one with Docker:

```bash
docker compose up -d
```

### 2. Python environment

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
# source .venv/bin/activate   # macOS/Linux
pip install -r requirements.txt
```

### 3. Configure `.env`

```bash
cp .env.example .env
```

Fill in:
- `PG_SUPERUSER_PASSWORD` — your local Postgres superuser password (used once, by the bootstrap step, to create the app's database and two roles)
- `GEMINI_API_KEY` — from [Google AI Studio](https://aistudio.google.com/) (or set `LLM_PROVIDER=fake` to run everything without any key)

### 4. Load the data

```bash
python scripts/load_data.py --bootstrap
```

`--bootstrap` creates the `ecommerce_analyst` database and two roles the
first time you run it (idempotent — safe to omit on subsequent runs):

- `analyst_owner` — owns the tables, used only by this loader
- `analyst_ro` — `SELECT`-only, used by the API (`DATABASE_URL` in `.env`)

This also writes `reports/data_quality.json`.

### 5. Run the API

```bash
uvicorn app.main:app --reload
```

Open `http://localhost:8000/docs` for interactive API docs.

### 6. Run the tests

```bash
pytest
```

All 51 tests pass with no `GEMINI_API_KEY` set and no database reachable —
they use `FakeChatModel` (a real `BaseChatModel`, not a mock) and stubbed
database tools. One test opportunistically checks the live schema and skips
itself if no database is reachable.

## Verification against the real dataset

The full pipeline — SQL validation → read-only execution → pandas analysis —
was verified against the live, fully-loaded PostgreSQL database (170,525 real
rows) for all ten required questions. Representative results:

| # | question | result |
|---|---|---|
| 1 | How many users are in the database? | **10,000** |
| 2 | Which products have the highest ratings? | NeoTech Stand leads at **4.9** |
| 3 | Which products generated the highest revenue? | Willow Result, **Rs. 73,525.32** |
| 4 | Which city has the most users? | North Michael, **13** users |
| 5 | Most common event types? | view 56,013 · cart 12,035 · wishlist 7,946 · purchase 4,006 |
| 6 | Products with many views, few purchases? | P000516 — 46 views, 1 purchase |
| 7 | Average order value? | **Rs. 595.93** |
| 8 | Which customers placed the most orders? | Michael Brown, **15** orders |
| 9 | Monthly order trend? | 23 months, Rs. 543,120 (Jan '24) → Rs. 278,040 (Nov '25, a partial month) |
| 10 | Category with the highest revenue? | Electronics, **Rs. 4,961,736.60** |

Every row above was produced by the actual `sql_validator` → `executor` →
`result_analyzer` code path in this repository against the real data — not
hand-calculated. `analyze_result()`'s computed extremes and sums match direct
verification queries (e.g. total revenue across categories sums to exactly
`SUM(order_items.item_total)`, `595.93` matches `AVG(orders.total_amount)`).
Question 9's apparent "decrease" is a genuine data artifact, not a bug: the
dataset ends 2025-11-14, so the final bucket is a partial month.

Live Gemini connectivity and the full classify → generate → validate →
execute → analyze → answer loop were also confirmed directly against this
database earlier in development. During the final verification pass, Google's
Gemini free tier was intermittently returning `503 UNAVAILABLE` ("high
demand") and `429 RESOURCE_EXHAUSTED` (daily free-tier quota) across every
available model — an external, account/service-side condition, not an
application bug. `app/llm/client.py` wraps the model with
`with_retry(stop_after_attempt=4, wait_exponential_jitter=True)` for exactly
this class of transient failure (with the client's own internal retry count
set to 0, so the two layers don't compound into multi-minute worst-case
latency — an issue caught and fixed during this verification pass). If the
outage persists, retry later, use a different/paid API key, or set
`LLM_PROVIDER=fake` to exercise the identical workflow with a deterministic
offline model.

## Security

- **SQL validation is Python code, not a prompt instruction**
  (`app/services/sql_validator.py`): the generated SQL is parsed with
  `sqlglot` into an AST; anything other than a single `SELECT` (optionally a
  `WITH ... SELECT`) is rejected, including write operations hidden inside a
  CTE or subquery. A second, keyword-level pass catches anything the AST
  check might miss (`pg_sleep`, `dblink`, psql meta-commands, `FOR UPDATE`,
  etc.), and multiple statements are rejected outright.
- **Read-only database role, not just a validator's promise**: the API
  connects as `analyst_ro`, which has `SELECT` only — no `INSERT`,
  `UPDATE`, `DELETE`, `CREATE`, or `DROP` privilege exists for that role at
  the database level. A hand-crafted `DELETE`/`CREATE TABLE` sent directly
  through `psql` as `analyst_ro` is refused by PostgreSQL itself (verified
  during development — see `reports/data_quality.json`'s sibling
  verification notes).
- **No string-interpolated SQL**: user input never gets f-string'd into a
  query; the validated SQL string is executed as a single opaque statement
  via SQLAlchemy.
- **Query limits**: every connection sets `statement_timeout`
  (`STATEMENT_TIMEOUT_MS`, default 15s); result sets are capped at
  `MAX_RESULT_ROWS` (default 500) with a `truncated` flag in the response.
- **API keys**: read from environment variables only
  (`app/config.py`, via `pydantic-settings`); `.env` is gitignored; nothing
  is hardcoded or logged.
- **Bounded repair loop**: on a validation or execution failure, the agent
  gets exactly one automated correction attempt with the error message
  attached, then reports failure — never an unbounded retry loop.

## Future improvements
